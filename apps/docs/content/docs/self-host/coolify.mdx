title: 用 Coolify 一键部署
description: 用 Coolify 的 Docker Compose 资源几分钟拉起 SwarmHive —— 默认直连服务器 IP,有域名可选 TLS
---

[Coolify](https://coolify.io) 是个自托管的 PaaS(Heroku / Netlify 平替)。这份模板**默认直连
服务器 IP 访问**(`http://<你的IP>:3030`,不经 Coolify 域名/反代)—— 适合没有域名、或 Coolify
分配的 `sslip.io` 域名在国内不可达的场景。DB / 存储的随机密码仍由 Coolify magic 变量自动生成。
**有域名想用 TLS?** 见下方「我有域名怎么办」。

## 步骤

1. **新建资源**:在 Coolify 项目里 → *New Resource* → **Docker Compose**(Empty)。
2. **粘贴 compose**:把下面这份直接粘进去保存(`server` + `postgres` + 可选 `rustfs`)。
   它和仓库
   [`deploy/coolify/docker-compose.yml`](https://github.com/swarm-apps/swarmhive/blob/main/deploy/coolify/docker-compose.yml)
   是同一份(文档构建时内联,不会漂移):

<include lang="yaml" meta='title="docker-compose.yml"'>../../../../../deploy/coolify/docker-compose.yml</include>
3. **填两个环境变量**(资源的 *Environment Variables*):`SWARMHIVE_SECRET_KEY`(见下方红框)
   和 `SWARMHIVE_SERVER__BASE_URL=http://<你的服务器IP>:3030`(对外地址,拼邮件链接用)。
4. **放行端口 + 部署**:在**云服务器安全组放行 `3030`**,点 Deploy。Coolify 把 server 发布到
   宿主机 `:3030`,并为 Postgres / RustFS 生成随机密钥。
5. **首启 bootstrap**:打开 `http://<你的服务器IP>:3030` → 自动跳 `/setup` 建第一个 Owner
   (邮箱 / 显示名 / 密码)。
6. **接入存储**:admin → *设置 → 存储* 向导,endpoint 填 `http://rustfs:9000`、bucket `swarmhive`、
   access/secret 用 Coolify 为 `RUSTFS` 生成的那对密钥(在资源的 Environment Variables 里能看到)→
   测试连通 → 激活。

<Callout type="info" title="RustFS 是可选的">
SwarmHive 的存储是 **S3-only**,RustFS 只是「单机自带存储」这一个选项。已经有
AWS S3 / Cloudflare R2 / MinIO / 阿里云 OSS,就**删掉 compose 里的 `rustfs` + `rustfs-init`
两个 service**(server 不依赖它们),第 6 步直接在向导里填你的 S3 endpoint / bucket / 凭证。
</Callout>

<Callout type="info" title="我有域名怎么办?(用 Coolify 域名 + TLS)">
想让 Coolify 自动出域名 + Let's Encrypt 证书,把 compose 里 server 改三处:

1. environment 第一项换回 `- SERVICE_FQDN_SERVER_3030`;
2. `SWARMHIVE_SERVER__BASE_URL` 改成 `=$SERVICE_URL_SERVER_3030`(自动用域名 URL,不必手填 IP);
3. `ports: ["3030:3030"]` 换回 `expose: ["3030"]`(不再直接发布到宿主机)。

然后**安全组放行 `80`/`443`**(而非 3030)。要 `SERVICE_FQDN` 生成**真实**域名,需要你的 Coolify
实例先配好 **wildcard 域名 + DNS**(*Settings → Instance Domain*);或在资源 **Domains** 字段手填自定义域名。
</Callout>

<Callout type="warn" title="访问不到 IP:3030?">
这份模板直接把 server 发布到宿主机 `:3030`,正常应能 `http://<你的服务器IP>:3030` 打开。打不开多半是:

- **云安全组 / 防火墙没放行 `3030`**(阿里云 / 腾讯云 ECS 默认不放行)—— 去安全组加一条入方向 TCP `3030`。
- **server 没起来**:在 Coolify 看该资源的 *Logs*,应有 `swarmhive-server listening addr=0.0.0.0:3030`;
  若反复重启,多半是 `SWARMHIVE_SECRET_KEY` 没填(必填,缺了启动即报错)。
</Callout>

## ⚠️ 关于 SWARMHIVE_SECRET_KEY —— 最关键的手动配置

<Callout type="warn" title="务必设定、固定不变、并备份">
SwarmHive 用一个对称密钥(AES-256-GCM)加密**落库的敏感字段**(邮件 provider 的 SMTP 密码,
将来还有 OAuth client_secret)。这个密钥从 `SWARMHIVE_SECRET_KEY` 读取,必须是
**base64 编码的 32 字节**:

```bash
openssl rand -base64 32
```

把输出粘到 Coolify 该资源的 **Environment Variables → `SWARMHIVE_SECRET_KEY`**。

- **一次设定后绝不要更改。** 密钥不支持轮换 —— 换了它,所有已加密的行(SMTP 密码等)就**再也解不开**。
- **务必备份它**(连同数据库一起)。丢了密钥 = 丢了所有已加密的密文。
- 这也是 server 在缺密钥时**启动即报错**(fail-fast)而不是随机生成的原因:一个会变的密钥比没有更糟。
</Callout>

<Callout type="info">
为什么不让 server 自动生成?因为自动生成只有在能**稳定持久化**时才安全;把密钥存进它自己保护的
那个数据库又会削弱“DB 泄露时密文仍安全”的初衷。所以这一步刻意留给你手动掌控 —— 仅此一个值。
</Callout>

## Coolify magic 变量做了什么

模板里这些 `SERVICE_*` 由 Coolify 在部署时自动生成 / 插值,**无需你填**:

| 变量 | 作用 |
| --- | --- |
| `SERVICE_PASSWORD_POSTGRES` | Postgres 随机密码,server 连接串与 `POSTGRES_PASSWORD` 复用同一个 |
| `SERVICE_USER_RUSTFS` / `SERVICE_PASSWORD_RUSTFS` | RustFS 的 access / secret key |

<Callout type="info">
这是个**模板**,Coolify 不同版本 magic 变量行为可能略有差异。若某个变量没按预期生成,在资源的
Environment Variables 面板里能看到 Coolify 实际生成的值,按需微调 compose 即可。
</Callout>

## 升级

Coolify 里点 *Redeploy* 即拉取最新 `ghcr.io/swarm-apps/swarmhive-server:latest`。镜像默认
`database.auto_sync = false`,生产不会跑 schema-sync,启动期只执行 `swarmhive-migration` 迁移账本。
要钉版本就把 compose 里的 `:latest` 换成 `:0.1.0` 这类语义化 tag。

## 不用 Coolify?

纯 docker compose / docker run / 单文件二进制的自托管方式见 [部署 Server](/docs/self-host)。
