这一页诚实地说明：哪些能力**现在就能用**，哪些还在**规划中（Phase 2）**。
SwarmHive 的第一阶段（MVP）专注把 **Tauri 桌面 + React Native Android** 的安装包更新主线打通——
自托管 Server、S3 兼容存储、`swarmhive` CLI 发布、headless SDK + shadcn 组件接入，
以及 v0.4.0 落地的通知与遥测分析。

## 当前已实现

更新发布主线已经端到端跑通：

| 能力 | 状态 | 说明 |
| --- | --- | --- |
| 自托管 Server | ✅ | Axum + Postgres + S3 兼容存储；单组织 RBAC + 邮件 + 通知 + scoped API Token |
| `swarmhive` CLI | ✅ | `init` / `verify` / `publish` / `apps` / `channels` / `releases` / `artifacts` / `storage` / `mail` / `notifications` / `telemetry` |
| Tauri 更新链路 | ✅ | 动态 updater endpoint，target / arch 匹配，签名元数据，强制更新与灰度字段 |
| React Native Android 链路 | ✅ | APK 更新检查，`versionCode` 比较，下载进度与系统安装器跳转 |
| headless SDK | ✅ | 8 态状态机 + ports & adapters + 灰度分桶（见 [SDK 概念](/docs/concepts)） |
| shadcn 组件 | ✅ | `registry-web`（Tauri/Web）与 `registry-rn`（RN）两套可复制源码 |
| 通知系统 | ✅ | 邮件 / webhook / IM provider 订阅、投递日志、自动重试、签名与密钥轮换 |
| 遥测分析 | ✅ | 更新链路事件、rollup 聚合、首页全局速览与 `/telemetry` 单 app 分析页 |

灰度发布（按 `client_id` 分桶让版本只对 X% 客户端可见）也已经可用——
服务端 `release.rollout_percent` 控制放量，客户端 `inRolloutBucket` 可复算同一结果。

## v0.4.0 已补齐的运营能力

- **通知**：发布、promote、rollback 可订阅到邮件、通用 Webhook 或 IM provider；投递日志支持四态、
  自动重试、手动重投、请求 / 响应快照和 attempt 时间线。见 [通知](/docs/self-host/notifications)。
- **遥测分析**：Server 可信事件 + SDK 自报事件进入 raw 表，再聚合到 event / device rollup；
  首页展示跨 app 速览，`/telemetry` 展示单 app 采用曲线、漏斗和分布。见
  [遥测与分析](/docs/self-host/analytics)。
- **策略编辑**：Admin 版本编辑抽屉与 `swarmhive releases update` 都能调整
  `rollout_percent`、`min_version`、`android_min_version_code`。

## 规划中（Phase 2）

下面是 SwarmHive 接下来的主要方向，**目前尚不可用**。

### ① OTA Provider（JS bundle 热更）

OTA（不发新安装包、只下发 JS bundle 热更）是 SwarmHive **明确规划但 MVP 不自研**的方向。
定位上它是一层 **Update Provider 扩展**：复用 SwarmHive 的应用 / channel / storage / CI-CD /
Admin / 遥测，而把具体 OTA 协议细节交给 provider，避免一上来就把 SwarmHive 做成
CodePush 或 Expo Updates 的竞争者。

候选方向**保持开放、不预选**，主要看落地时的真实需求：

| 候选 provider | 适合谁 |
| --- | --- |
| 自托管 Expo Updates | 已经在用 expo-updates、按 runtime version / branch / channel 管理的项目 |
| External OTA Sync | 已经自建了 Expo / CodePush server，只想让 SwarmHive 统一 Admin / 统计 / 存储 |

MVP 阶段只**留架构接缝、不落实现**：OTA release 与 native release 分开建模、可关联，
未来 OTA bundle 的可下发性靠 runtime version / fingerprint 精确匹配，**不复用**现有
APK `versionCode` 或 Tauri semver 的整数 / semver 闸门——Phase 2 会另立兼容键，
而不是现在就在 release 表里建占位列。

<Callout type="info">
**OTA 热更尚未实现，也没有 `swarmhive ota` 命令。** MVP 只覆盖 Tauri 整包更新与
Android APK 更新两条主线；JS bundle 热更是 Phase 2 的 provider 扩展层，候选 provider
（自托管 Expo Updates / External OTA Sync）保持开放，等真实需求出现再选一个做 PoC。
SwarmHive 不承诺所有 RN 项目都能无改造接入 OTA，也不绕过 App Store 审核规则。
</Callout>

## 其他规划项

除 OTA 外，以下能力也在 MVP 之后的清单里（顺序不代表优先级）：

- 多实例 server：session 共享、后台任务 leader election、通知 / telemetry worker 外置队列。
- OTA provider 的 runtime version / fingerprint 兼容键与 provider 管理界面。
- 更多 S3 兼容存储配置示例与镜像策略。
- SDK UI 更完整的组件集与主题预设。
