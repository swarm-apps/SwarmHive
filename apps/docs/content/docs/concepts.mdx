`@swarm-hive/sdk` 是整套更新 UI 的内核。理解这三个概念，你就能看懂每个组件在做什么、为什么这么拆。

## Ports & Adapters

SDK 的引擎**零平台依赖**——它不知道 Tauri、不知道 React Native、不知道 fetch。
所有平台相关的事都收敛到一个接口 `UpdateAdapter`（即 "port"）：

```ts
interface UpdateAdapter {
  // 问服务端有没有更新（平台各自实现：Tauri 走 plugin-updater，RN 走 HTTP）
  check(ctx: CheckContext): Promise<ReleaseInfo | null>;
  // 下载更新包，期间回调进度
  download(release: ReleaseInfo, onProgress: (p: Progress) => void): Promise<DownloadHandle>;
  // 安装（+重启 / 交给系统安装器）
  install(handle: DownloadHandle): Promise<void>;
  // 持久化 KV（last_checked / dismiss / client_id）
  storage: KeyValueStorage;
  // 版本比较：当前版本 vs 候选 release 是否算「更新」
  compare(current: string, candidate: ReleaseInfo): boolean;
}
```

`shadcn add` 给 Tauri 带来的 `lib/tauri-adapter.ts` 就是这个接口的一份实现（"adapter"）。
要支持新平台，只需写一个新 adapter，引擎和所有 UI 组件**一行不改**。

引擎本身用 `createUpdateEngine(adapter, opts)` 装配，返回一个 zustand vanilla store；
React 侧用 `useUpdateEngine(engine)` 订阅。本套组件把这层封装成了 `<UpdateProvider>` + `useUpdate()`。

## 8 态状态机

引擎把「更新」这件事建模成 8 个状态。组件只是这些状态的**视图**——
弹窗开不开、按钮显示「立即更新」还是「下载中…」，全看当前状态。

```text
                 check()
   idle ───────────────────────► checking
                                    │
              ┌─────────────────────┼─────────────────────┐
              ▼                     ▼                     ▼
         up-to-date            available            force-required
         （已最新）          （可选更新）         （强制更新）
                                  │                     │
                                  └──────── download() ──┘
                                            │
                                            ▼
                                       downloading ──► ready ──► install()
                                            │
                                            ▼  （任意阶段出错）
                                          error ──► retry()
```

| 状态 | 含义 | 谁在这态渲染 |
| --- | --- | --- |
| `idle` | 初始，还没检查 | —— |
| `checking` | 正在请求服务端 | 设置项显示「检查中…」 |
| `up-to-date` | 已是最新 | 设置项显示「已是最新」 |
| `available` | 有可选更新（`upgradeType: "prompt"`） | `PromptUpdateDialog` |
| `force-required` | 有强制更新（`upgradeType: "force"`） | `ForceUpdateDialog` |
| `downloading` | 下载中，带 `progress` | `UpdateProgressDialog` / 弹窗内进度条 |
| `ready` | 下载完成，待安装 | 弹窗按钮变「正在重启…」 |
| `error` | 任意阶段失败，带 `UpdateError` | 设置项显示错误 + 重试 |

引擎还内置了几个**生产级细节**：

- **节流**：非强制 `check()` 在 `recheckIntervalMs`（默认 12h）内不重复打服务端。`check(true)` 绕过。
- **dismiss-TTL**：用户点「稍后」后，同一版本在 `dismissTtlMs`（默认 24h）内不再标 `available`（强制更新不受影响）。
- **句柄缓存**：下载得到的平台句柄不可序列化，存在闭包里，`install()` 复用，失败后丢弃重下。

## 灰度分桶

服务端可以让一个版本只对 X% 的客户端可见（灰度发布）。判定落在客户端，靠两样东西：

1. **稳定的 `client_id`**——`ensureClientId(storage)` 首次生成一个随机 ID 并持久化，之后每次复用。
   它经请求头 / query 传给服务端，保证「同一台设备每次分桶结果一致」（不会今天命中、明天又不命中）。
2. **分桶函数**——`inRolloutBucket(clientId, percent)` 把 `client_id` 哈希到 `[0, 100)`，
   小于 `percent` 即命中。它是纯函数、确定性的，服务端与客户端用同一套算法即可对齐。

```ts
import { ensureClientId, inRolloutBucket } from "@swarm-hive/sdk";

const clientId = await ensureClientId(adapter.storage); // 稳定标识
inRolloutBucket(clientId, 20); // 该客户端是否在 20% 灰度内
```

<Callout type="info">
在 SwarmHive 的直连部署里，灰度判定主要由**服务端**完成（它最知道当前 rollout 配置）；
`inRolloutBucket` 导出是为了让客户端 / 测试也能复算同一结果。Tauri 的 adapter 会自动把
`client_id` 放进 `X-Client-Id` 头随 `check()` 上送。
</Callout>
